\begin{abstract}
Parallelising symbolic reachability for timed automata is, in outline, a solved
problem: the zone-graph successor function is pure, so expansions within a BFS
level are independent.  We built such an engine---level-synchronous BFS over a
lock-striped shared passed list---and measured it running at $99.8\%$ parallel
efficiency, with cumulative load imbalance of $4$~ms in a $6.9$~s run.  It still
beat sequential UPPAAL by only $\approx 1.5\times$ on twelve cores.

This paper reports what was actually limiting it, and we believe both causes
generalise.  The first is a reclamation trigger latched on a monotone counter,
which turned an occasional serial mark-and-sweep into a per-level one whose cost
grows with the state space---a textbook Amdahl term, worth $30\%$ of wall-clock
time at scale, and invisible on the small models used during development.  The
second is subtler and is our main contribution.  Passed zones are stored as
minimal constraint systems, a standard $\approx 12\times$ memory saving; but the
zone algebra needs dense closed matrices, so every subsumption query first
rebuilt one, at $O(|\clocks|^3)$.  With $89.8\%$ of insertions being duplicates
rejected by the first test, against antichains of mean length $1.00$, we spent
$22\times$ longer decompressing stored zones than comparing against them.  We
call this the \emph{compression tax}: a representation optimised for bytes
resident and silently taxed on cost per query---and parallelism hides it, because
the tool still scales, just from a worse constant.

We remove it by deciding inclusion directly against the minimal constraint
system in $O(|G|)$, and composing that exact test as a sound pre-filter for the
coarser $\preceq_{aLU}$ abstraction the engine prunes with.  We prove the
composite explores exactly the same states, and confirm it empirically state
count for state count.  On families where passed-list traffic dominates the two
fixes compose to $2.4\times$ over our own baseline; where it does not, the
second correctly does nothing, and we report both.  Against UPPAAL~5.0 the
resulting engine is $2.2$--$5.2\times$ faster across the families we measure.
\end{abstract}
